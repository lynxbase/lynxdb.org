Search is the first step

You find the error, then you ask how often, where and since when. LynxDB runs the search and the analytics in one engine, with one pipe language: OpenSearch PPL.

Query
source=main "connection refused" earliest=-1h
| fields _time, host, msg
| head 5

Words and quoted phrases match in every field of an event, in any case. Blocks that cannot hold the phrase are skipped before they are read.

Query
source=main user=grace status>=500
| fields _time, host, path, status, response_time
| sort - _time

An exact field match uses that field's own token filter, so a user, a trace ID or an IP is as cheap to follow as a log level. There is no schema to declare first.

Query
source=main
| stats count() as total,
        count(eval(status >= 500)) as errors by host
| eval error_rate = round(errors * 100.0 / total, 1)
| sort - error_rate

Aggregations run on the columnar engine and decode only the columns the query names.

Query
source=main level=ERROR OR level=WARN earliest=-1h
| timechart span=1m count() by level

Each block stores its row counts by minute, hour and day, so many time charts add up stored buckets instead of reading rows.

Why search is fast

A search reads only the blocks that can match. There is no global posting list to maintain, so ingest stays cheap and the index stays small.

earliest=-1h
Outside the time rangeSkipped by token filterRead and verified

  1. Time first

    Events are stored in time partitions. A query with a time range never opens the partitions and blocks outside it.

  2. Token filters

    Every block carries compact fingerprints of the tokens inside it. If a block cannot hold your word or your field value, it is skipped without being read.

  3. Only the columns you ask for

    Storage is columnar. A query decodes the columns it names, and settles filters such as status >= 500 from block metadata when it can.

Built for logs

Any log, no schema

JSON keeps its fields. Plain text gets its timestamp, key=value pairs and common formats such as access logs and syslog extracted on the way in.

2025-01-15T08:00:00.105Z host=web-03 level=ERROR method=GET path=/api/v1/users status=502 user=grace response_time=786

OpenSearch PPL

One pipe language for search, filters, stats, time charts and joins. Nothing proprietary to learn.

Compact storage

Columnar parts with dictionary encoding, Zstandard and LZ4. Retention drops whole time partitions.

Keep your collector

Point the agent you already run at a new address.

Open source

Apache 2.0. One static binary with no runtime dependencies.

A file, a pipe or a server

The same engine answers over a local file, the output of another command, or a server that stores logs on disk.

$ kubectl logs deploy/api | lynxdb query 'source=main status>=500 | top 10 uri'

Install LynxDB

The script detects your architecture, downloads the matching release, checks it against the published SHA-256 sums and installs the binary to /usr/local/bin.

All installation options -> 
curl -fsSL https://lynxdb.org/install.sh | sh
brew install lynxbase/tap/lynxdb
docker run -d --name lynxdb -p 3100:3100 \
  -v lynxdb-data:/data ghcr.io/lynxbase/lynxdb \
  server --addr 0.0.0.0:3100 --data-dir /data
go install github.com/lynxbase/lynxdb/cmd/lynxdb@main

Static binary for amd64, arm64 and armv7. Runs on glibc and musl.

Start with a log file you already have

$ lynxdb query --file access.log 'source=main status>=500 | top 10 uri'
